# ADR-0001: 개인 개발 기록 체계 — 위치 · 형식 · 발동 방식

상태: 채택 · 결정: 2026-08-28

## 맥락

**외부 제약**
- 프로젝트 레포(S15P21E103)는 SSAFY GitLab의 팀 공유 레포다. 레포에 들어가는 파일은 전부 팀원에게 간다 — 프로젝트 `CLAUDE.md`, `.claude/` 도 커밋 대상이다
- 팀 문서는 Cushion `penguin-milk` 라이브러리에 있고 레포에는 스펙(`specs/`)만 있다
- 나는 Orca 워크트리에서 작업한다. 워크트리는 작업이 끝나면 지워진다
- 이 기록의 용도는 블로그·자소서다. 사후 각색이 섞이면 값어치가 없다
- 직전 프로젝트 SeCoMe(영상 회의 기반 문서 협업 서비스)에서 AI와 문서를 함께 썼는데, 세션이 끊길 때마다 형식을 다시 설명해야 했다. 품이 들었고 문서마다 형식이 흔들렸다

**충돌**
- 기록을 코드 옆에 두면 찾기 편하다 ↔ 팀 레포에 개인 기록이 섞이고, 워크트리와 함께 사라진다
- AI가 형식을 항상 알게 하려면 `CLAUDE.md`가 가장 확실하다 ↔ 프로젝트 `CLAUDE.md`는 팀에 공유되고, `~/.claude/CLAUDE.md`는 관계없는 프로젝트에도 딸려온다
- 형식을 스킬 한 파일에 다 넣으면 단순하다 ↔ 형식은 바뀌는데 두 곳에 있으면 어긋난다

**판단 기준**
세션이 바뀌어도 형식이 유지되는가를 1순위로 봤다 — SeCoMe에서 든 품이 계기였다.
팀 레포에 아무것도 들어가지 않는 것은 협상 대상이 아닌 제약으로 놓았다.

## 결정

개인 기록을 레포 밖 `~/Desktop/penguin-devlog/`에 두고, 형식은 각 폴더의 README에만 쓰고,
Claude가 그 README를 읽어 쓰도록 하는 개인 스킬 `~/.claude/skills/devlog/`를 만들었다.

구체적 형태:
- **위치**: `~/Desktop/penguin-devlog/`, 자체 `git init`. 프로젝트 레포와 무관
- **폴더 5개**: `adr/` 결정 · `infra/` 인프라 작업 · `backend/` 구현 · `troubleshooting/` 장애 추적 · `review/` 코드 이해.
  각 폴더는 답하는 질문 하나와 품질 기준 하나를 가진다
- **형식 단일 출처**: 루트 README(공통 규칙 — frontmatter·문체·갱신·인덱스) + 폴더 README(섹션 순서).
  스킬에는 형식을 복사하지 않는다
- **스킬 위치**: 레포 안 `skill/devlog/`가 원본, `~/.claude/skills/devlog`는 정션. GitHub `1Irving1/penguin-devlog`(private)에 기록과 함께 올린다
- **스킬**: 폴더 라우팅 표 + 6단계 절차(폴더 선택 → 기존 파일 확인 → README 읽기 → 사용자만 아는 것 묻기 → 작성 → 인덱스) + 놓치기 쉬운 것

범위 경계: 팀 문서(Cushion)에는 적용하지 않는다. 자동 트리거는 없다 — 내가 요청해야 쓴다.
코드 컨벤션·커밋 규칙은 다루지 않는다.

## 근거

- **레포 밖에 둔다** → 커밋 실수가 구조적으로 불가능하고, 워크트리 삭제와 무관하며, 나중에 블로그 레포로 그대로 push할 수 있다
  - 기각: 레포 안 `devlog/` + `.git/info/exclude` — exclude는 클론별 로컬 설정이라 워크트리마다 다시 해야 하고, 워크트리가 지워지면 기록도 같이 지워진다
  - 기각: Cushion 개인 라이브러리 — 팀 도구에 개인 기록이 섞이고, 로컬 파일이 아니라 블로그로 옮길 때 한 단계가 더 생긴다
- **스킬로 발동한다** → 필요할 때만 컨텍스트에 로드되고, `~/.claude/`라 팀에 가지 않고, 트리거 문구로 부를 수 있다
  - 기각: 프로젝트 `CLAUDE.md` — 커밋되어 팀원 세션에도 적용된다
  - 기각: `~/.claude/CLAUDE.md` — 이 프로젝트와 무관한 세션에서도 매번 컨텍스트를 먹는다
- **형식은 README에만 둔다** → 형식을 고칠 때 한 곳만 고치면 되고, 스킬이 낡은 형식을 기억할 수 없다.
  비용은 호출마다 README 2개(약 150줄)를 읽는 것 — 감수했다
- **폴더마다 품질 기준을 한 문장으로 박는다** → "잘 썼나"를 판정 가능한 질문으로 바꾼다.
  AI가 그럴듯하게 채우는 것을 막는 장치다 (troubleshooting: 틀린 가설이 몇 개인가 · review: 질문을 읽기 전에 박제했나 · adr: 부정·제약이 비어 있지 않나)
- **쓰기 전에 사용자만 아는 것을 묻는다** → 계기·당시 판단·소요 시간을 추정으로 메우지 않는다. 자소서 용도에서 이게 핵심이다

## 결과

### 긍정
- 새 세션에서 형식 설명이 0이다. "ADR로 박아줘" 한 마디로 끝난다
- 프로젝트 레포와 팀원에게 아무것도 가지 않는다 (`git status` 두 체크아웃 모두 clean 확인)
- 형식 개정이 README 편집 하나로 끝난다
- frontmatter가 처음부터 있어 블로그 이전 시 일괄 편집이 없다

### 부정·제약
- 자동으로 쓰지 않는다. 기록을 잊으면 그냥 없다
- 결정/작업/이해의 경계 판단이 매번 Claude에 위임된다. 잘못 분류될 수 있다
- 다른 PC에서는 클론 + 정션 한 번을 손으로 해야 한다. 스킬 경로가 `~/Desktop/penguin-devlog`로 박혀 있어 위치를 바꾸면 SKILL.md도 고쳐야 한다
- 형식을 문서 0개 상태에서 만들었다. 실제로 5~10개 쓰고 나면 손봐야 할 확률이 높다
