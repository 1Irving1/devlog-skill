# blog — 개인 기술 블로그 글쓰기

재료는 `dev-journal`의 기록과 작업 세션. 글은 `dev-journal/projects/blog/posts/YYYY-MM-DD-slug.md`.

## 순서

1. **재료를 확인한다** — 어떤 기록·세션을 글로 만들지. 애매하면 묻는다
2. **앵글 하나를 정한다** — 독자가 이 글에서 가져갈 것 한 문장.
   정하지 못하면 쓰지 않고 사용자에게 묻는다. 앵글 없는 글은 기능 소개가 된다
3. 골격대로 배치하고, 문체 규칙대로 쓴다
4. **자기 점검**을 돌린다
5. `docs` 타입으로 커밋·push

## 골격

| 섹션 | 내용 |
|---|---|
| 계기 | 무엇이 불편했는지. **장면으로 시작한다** — 기능 소개로 열지 않는다 |
| 갈림길 | 선택지가 무엇이었고 왜 그걸 골랐는지 |
| 핵심 하나 | 독자가 가져갈 것. **가장 길게 쓴다** |
| 함정 | 실제로 겪은 문제 |
| 아직 모르는 것 | **정확히 2개** |
| 정리 | **정확히 2개** |

한계와 정리를 2개로 묶는 이유 — 셋을 넘기면 독자가 무엇이 중요한지 못 고른다.
더 쓰고 싶으면 본문에 녹인다.

## 문체

- **같은 종결어미를 3번 연속 쓰지 않는다.** "~다. ~다. ~다."는 보고서지 글이 아니다
- **문장 길이를 변주한다.** 긴 설명 다음엔 짧게 끊는다
- 문장을 이어 쓴다 — "~했는데", "~더니", "~고 보니", "~기로 했다", "~인 셈이다"
- 한 단락은 5줄 이내. 넘으면 자른다
- **표는 대비가 있을 때만.** 단순 나열은 산문으로 푼다
- 목록이 세 덩어리 연속이면 하나는 문장으로 바꾼다
- 질문을 던져도 된다. 실제 프롬프트·대화는 인용으로 원문 그대로
- 부사를 남용하지 않는다 — "매우", "정말", "굉장히"
- 1인칭 과거형. 겪은 일은 겪은 대로

## 하지 않는 것

- **도구 자랑.** 무엇을 만들었나가 아니라 무엇이 불편했나에서 출발한다
- 첫 단락에 결론 요약 붙이기
- 안 겪은 일 쓰기. 기록에 없으면 지어내지 말고 묻는다
- 정리에서 새 얘기 꺼내기

## 예시 — 규칙이 실제로 무엇을 바꾸나

같은 내용, 규칙 적용 전후.

**전** (종결어미 3연속, 문장 길이 균일 → 보고서)
> 문제는 내용이 아니라 형식이었다. 세션이 끊기면 AI는 형식을 기억하지 못한다. 그래서 나는 다시 설명했다.

**후** (짧게 끊고 → 길게 풀고 → 다른 어미로 마무리)
> 쓰는 것 자체는 어렵지 않았는데 매번 걸리는 게 형식이었다. (…) 한 번은 괜찮다. 스무 번쯤 되니 품이었다. 게다가 설명이 조금씩 달라지는 바람에 문서마다 형식이 미세하게 흔들렸고, 나중에 모아 읽으니 같은 저장소인데 결이 제각각이더라.

섹션 제목도 같다. "AI가 그럴듯하게 채우는 것을 막는 장치"보다
"AI는 빈칸을 너무 잘 메운다"가 낫다 — 명사구 대신 문장으로.

## 자기 점검

쓴 뒤 확인한다. 걸리면 고치고 다시 본다.

- 같은 종결어미가 3연속인 곳이 없나
- 아직 모르는 것 2개, 정리 2개인가
- 표가 진짜 대비를 담고 있나 (아니면 산문으로)
- 첫 세 줄에 장면이 있나
- 섹션 제목이 명사구가 아니라 문장인가
- 한계를 정직하게 썼나 — 자랑으로 끝나지 않았나
